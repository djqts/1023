## 1. 背景、目标与范围

### 1.1 背景

网络扫描会产出大量 `ip`、`port`、`banner` 原始数据。banner 可能来自 SSH、HTTP、MySQL、Redis、FTP 等服务，格式差异大，且经常被截断、包含二进制字节或噪声。人工逐条判断协议、软件和版本效率低、不可复用。

需要建设一个批量识别服务：接收扫描原始数据，输出结构化的协议/产品/版本/OS 线索/置信度；识别不了的条目返回 `unknown`，不能报错或崩溃；并以 client + server、Docker Compose 一键启动的方式交付。

### 1.2 目标

| 编号 | 目标 |
|---|---|
| G-01 | 对一批扫描数据完成协议、产品、版本、OS 线索和置信度识别 |
| G-02 | 认不出时稳定返回 `unknown`，不因单条数据异常导致请求失败或服务退出 |
| G-03 | 提供独立的 client 与 server，Compose 一键启动并完成端到端演示 |
| G-04 | 达到“生产级部署”基线：访问收敛、真实健康检测、镜像与权限收紧、规则与代码解耦 |

### 1.3 范围

| 范围 | 内容 |
|---|---|
| 纳入 P0 | SSH、HTTP（nginx/Apache/Jetty）、MySQL、Redis、FTP；两个 HTTP 接口；CLI client；Compose 双服务；基础安全与规则外置 |
| 纳入 P1 | 二进制安全输入、更多协议/产品、客户端重试与分片、规则热加载、运行时资源限制、性能调优 |
| 纳入 P2 | 鉴权、限流、指标/追踪、规则管理平台、水平扩展、持久化、主动探测/ML、Web UI |
| 不纳入 | 主动连接目标、漏洞判定、全协议库、机器学习训练、多租户 |

### 1.4 术语

| 术语 | 定义 |
|---|---|
| Banner | 服务端在连接建立后发送的原始字节，可能包含多行文本或二进制 |
| 指纹 | 能从 banner 中区分协议、产品、版本、OS 的特征 |
| 识别深度 | 输出中协议、产品、版本、OS 线索、置信度的完整程度 |
| unknown | 无法识别时的统一结果，`protocol="unknown"`，其余字段为空，置信度为 0 |
| 规则 | 外置的声明式识别配置，描述“什么特征 → 什么协议/产品/版本” |
| P0/P1/P2 | 见 1.5 |

### 1.5 优先级与编号规则

| 级别 | 定义 | 判定标准 |
|---|---|---|
| P0 | 通过验收的最小闭环 | 缺少任一项，题目硬性要求或评估重点不满足 |
| P1 | 重要但非阻塞 | 不影响最小闭环，但明显影响生产可用性、可运维性或评价 |
| P2 | 优化与扩展 | 锦上添花，资源允许时再做 |

编号规则：`F-P0-xx` 为 P0 功能，`P1-xx`/`P2-xx` 为后续功能，`NFR-xx` 为非功能需求，`C-xx` 为约束，`Q-xx` 为待定事项。

## 2. 功能分析

### 2.1 P0 核心功能

#### 2.1.1 识别能力

##### F-P0-01 协议识别

**需求描述**：系统必须从 banner 识别 SSH、HTTP、MySQL、Redis、FTP 五类协议；无法识别时返回 `unknown`。端口只能作为辅助证据，不能作为唯一判据。

**业务规则**：

- 协议值统一小写：`ssh`、`http`、`mysql`、`redis`、`ftp`、`unknown`。
- 强签名优先于端口先验；例如 2222 端口的 SSH 仍应识别为 `ssh`。
- 不得把 SMTP 的 `220` 问候误判为 FTP；FTP 判定必须包含 FTP 产品特征。
- 同一输入、同一规则版本，输出必须一致。

**验收标准**：

- 五类协议各至少 2 个真实横幅夹具，协议识别全部正确。
- 端口变化（如 SSH 2222、HTTP 8080）不影响正确识别。
- 负例：SMTP `220 ... ESMTP`、随机二进制、空 banner，均返回 `unknown`。
- 附录 B 的基线样例全部通过。

##### F-P0-02 产品、版本与 OS 线索

**需求描述**：在协议识别的基础上，输出产品名、版本号和 OS 线索；无法提取时留空，不得编造。

**业务规则**：

- 产品名使用统一规范名，例如 `OpenSSH`、`nginx`、`Apache`、`Jetty`、`MySQL`、`MariaDB`、`Redis`、`vsftpd`、`ProFTPD`、`Microsoft FTP Service`。
- 版本精确到 banner 中可提取的粒度；能到补丁号就到补丁号（如 `8.2p1`、`1.18.0`），提取不到完整版本时留空，不输出半截版本。
- `os_hint` 只根据 banner 中的证据填写（发行版标记、Windows 产品名等）；没有证据时为空字符串。
- Redis 只返回 `+PONG` 等无版本信息时，`version=""` 是正确结果。
- 只有 ip/port/banner 三个输入，不做 TTL、主动 OS 探测等推断。

**验收标准**：

- 附录 B 基线样例的 `product`、`version`、`os_hint` 全部匹配。
- 不出现凭端口猜测产品/版本的情况。
- 示例补充后，以示例的命名和粒度为最终标准。

##### F-P0-03 unknown 兜底与稳定性

**需求描述**：任何无法识别的条目都必须稳定返回 `unknown`，不得导致整批失败、HTTP 5xx 或进程退出。

**业务规则**：

- unknown 结果固定为：`protocol="unknown"`、`product=""`、`version=""`、`os_hint=""`、`confidence=0`。
- 单条数据的异常（空 banner、乱码、NUL、非法 UTF-8、超长、截断、正则元字符）只影响该条。
- 服务端必须有 panic 隔离；单条处理异常降级为 unknown，整批继续。
- 请求结构错误返回 4xx；识别失败返回 200 + unknown，两者不得混淆。

**验收标准**：

- 空 banner、随机二进制、NUL、非法 UTF-8、截断 SSH/HTTP、含正则元字符的 banner 均不导致 5xx/崩溃。
- 10,000 条 unknown 批量请求返回 200，进程存活。
- 模糊测试持续 60 秒无 panic。
- 单条异常后，同批其他条目结果正确。

##### F-P0-04 置信度

**需求描述**：每条结果必须给出 0~1 的置信度，用于表达识别证据强度。

**业务规则**：

- 取值范围 `[0,1]`；unknown 固定为 0；已识别结果大于 0。
- 置信度是规则证据强度的启发式分数，不承诺是校准概率。
- 计算必须确定性：同一输入、同一规则版本，多次调用结果一致。
- 只有端口、没有 banner 证据时，不得仅凭端口输出协议。
- 置信度规则写入规则文档，可解释、可回归。

**验收标准**：

- 所有输出在 `[0,1]` 内。
- unknown 为 0。
- 同一请求重复 100 次，结果完全一致。
- 置信度与证据强度单调一致（产品+版本 > 只有产品 > 只有协议）。

#### 2.1.2 服务接口

##### F-P0-05 批量识别接口 `POST /fingerprint`

**需求描述**：接收一批扫描数据，返回逐条识别结果。

**请求约定（暂定，待示例确认）**：

- `Content-Type: application/json`。
- 请求体：`{"items":[{"ip":"...","port":22,"banner":"..."}]}`。
- `ip` 为字符串；`port` 为 1–65535 的整数；`banner` 为字符串，可为空。
- 单批最多 10,000 条；请求体最大 8 MiB；单条 banner 最大 16 KiB；请求超时 30 秒。
- 允许空数组，返回空结果。

**响应约定**：

- `200`：`{"results":[...]}`，每条严格包含 `ip`、`port`、`protocol`、`product`、`version`、`os_hint`、`confidence` 七个字段。
- 结果顺序与输入顺序一致；不额外返回 `evidence`、`rule_id` 等字段。
- unknown 条目也返回 200，不返回错误。

**错误约定**：

| 场景 | HTTP | 说明 |
|---|---|---|
| 正常处理（含全部 unknown） | 200 | 逐条结果 |
| JSON 结构/类型/必填字段错误 | 400 | 不进入识别 |
| 超过条数/体积/banner 限制 | 413 | 明确提示限制 |
| 方法错误 | 405 | 返回 `Allow` |
| 内部错误 | 500 | 带 `request_id`，不泄露内部细节 |
| 过载/停机中 | 503 | 可重试 |

**验收标准**：

- 1 条已识别 + 1 条 unknown，返回 200、两条结果、顺序正确、字段齐全。
- 全部 unknown 返回 200。
- 畸形 JSON 返回 400，进程不退出。
- 10,001 条返回 413。
- `GET /fingerprint` 返回 405。
- 空数组返回 200 和空结果。

##### F-P0-06 健康检查接口 `GET /health`

**需求描述**：提供真实反映服务就绪状态的健康检查，供 Compose 和运维使用。

**业务规则**：

- 仅在规则加载完成、服务可接收请求时返回 200。
- 未就绪、正在停机或规则不可用时返回 503。
- 响应为 JSON，至少包含：`status`、`version`、`rules.count`、`rules.digest`、`uptime_s`。
- 健康检查不执行识别、不读取 banner、不需要鉴权。
- 健康检查必须验证业务就绪，不能只检查端口存活。

**验收标准**：

- 启动完成后返回 200，`status="ok"`，`rules.count>0`。
- 规则文件损坏时服务不进入健康状态（启动失败或 503），并在日志中给出明确原因。
- Compose healthcheck 使用该接口，且退出码能真实反映 200/503。
- `/health` 的 p95 响应时间不超过 100ms。

#### 2.1.3 客户端

##### F-P0-07 客户端读取、发送与展示

**需求描述**：client 是独立程序，读取本地 JSON 文件，调用 server，并把识别结果展示给用户。

**业务规则**：

- 支持参数：`-server`（server 地址）、`-input`（本地 JSON 文件路径）；server 地址可通过环境变量提供。
- Compose 中默认 server 地址为 `http://server:8080`，不得使用 `localhost` 或宿主 IP。
- 默认以表格展示七个字段，并给出总数/unknown 数汇总；unknown 正常展示，不标为错误。
- 结果写 stdout，日志写 stderr，便于管道和脚本消费。
- 退出码：`0` 表示全部处理完（含 unknown）；`1` 表示网络/服务端错误；`2` 表示用法或输入文件错误。
- client 不内嵌识别规则，识别逻辑只在 server。
- P0 支持不超过 server 单批限制的文件；超过限制的分片与重试属于 P1。

**验收标准**：

- 示例输入经 client 展示后，包含五类协议和至少一条 unknown。
- server 停止时，client 以非 0 退出并给出清晰错误，不崩溃。
- 全部 unknown 的输入，client 退出码为 0。
- client 可在 Compose 内运行，也可在宿主机直接运行并访问 `127.0.0.1:8080`。

#### 2.1.4 交付与部署

##### F-P0-08 Docker Compose 一键启动

**需求描述**：在具备 Docker 环境的干净机器上，一条命令完成构建、启动、等待健康、执行 client、输出结果。

**业务规则**：

- 入口命令：`docker compose up --build`。
- server 先启动并通过健康检查，client 再启动；client 执行完退出，server 保持运行。
- 提供示例输入文件，挂载为只读；不要求用户手动构建镜像或初始化数据。
- `docker compose down` 能干净停止。
- Compose 顶层固定项目名，避免中文目录名推导出意外项目名。

**验收标准**：

- 干净环境执行 `docker compose up --build`，无需额外手工步骤即可看到识别结果。
- `docker compose ps` 中 server 为 healthy。
- client 退出码为 0，结果包含预期协议。
- 可通过 `docker compose run --rm client` 重复执行。
- README 明确说明 client 退出后 server 仍运行的预期行为。

##### F-P0-09 容器间访问收敛与真实启动依赖

**需求描述**：容器间只保留必要的访问路径；client 必须等 server 真正就绪后再启动。

**业务规则**：

- client 通过 Compose 服务名访问 server：`http://server:8080`。
- 禁止使用 `localhost`、`127.0.0.1`（容器内）、宿主 IP、`host.docker.internal` 访问 server。
- 只发布 server 的 8080，并绑定到宿主机 `127.0.0.1`；不发布 client，不发布其他端口。
- `depends_on` 必须使用 `condition: service_healthy`，不能只写服务名。
- healthcheck 必须是业务级检查（HTTP 200 + 业务状态），不能只检查进程或端口存活；在 distroless 运行时不得依赖 shell/curl。
- 容器运行时不得使用 host 网络。

**验收标准**：

- `docker compose config` 中仅出现 `127.0.0.1:8080:8080` 一条端口映射。
- client 配置中 server 地址为服务名，不含宿主地址。
- server 不健康时，client 不会提前启动/执行。
- healthcheck 在 `/health` 返回 503 时失败。

##### F-P0-10 镜像与运行权限基线

**需求描述**：镜像体现多阶段编译和最小运行时的理解；容器以最小权限运行。

**业务规则**：

- 构建采用多阶段：构建阶段编译，运行阶段只保留静态二进制和必要证书。
- 运行镜像不包含 shell、包管理器和源码；优先使用 distroless/scratch 类基础镜像。
- 容器以非 root 用户运行（如 UID 65532），不得使用 root。
- 根文件系统只读；规则和数据以只读方式挂载。
- 丢弃全部 Linux capabilities；启用 `no-new-privileges`。
- 服务监听 8080，不使用需要特权的端口。
- 镜像中不包含识别规则文件，规则通过挂载提供。

**验收标准**：

- `docker inspect` 显示非 root 用户、`ReadonlyRootfs=true`、`CapDrop=["ALL"]`、`no-new-privileges`。
- 运行镜像内不存在 `/bin/sh`。
- 容器内进程 UID 非 0。
- 服务在只读根文件系统下正常运行。
- 镜像大小不超过 30 MB（目标值，允许因基础镜像差异略有浮动）。

##### F-P0-11 规则与程序代码解耦

**需求描述**：识别规则必须外置、可独立修改和校验，新增规则不需要修改 Go 代码或重新构建镜像。

**业务规则**：

- 规则存放在独立目录的 YAML 文件中，通过只读卷挂载进容器。
- Go 代码只实现通用的匹配原语和处理流程，不硬编码产品名、版本正则或协议专属分支。
- 启动时加载并校验规则；非法正则、重复 ID、缺失捕获组、置信度越界等必须 fail fast，并指出文件与行号。
- `/health` 暴露规则数量和内容摘要（digest），便于确认运行的是哪一版规则。
- 规则 schema 带版本号，便于后续兼容演进。
- 规则文件不得 COPY 进运行镜像。

**验收标准**：

- 新增一条测试规则并重启 server，无需重新构建镜像即可识别新特征。
- 规则文件写错时，server 启动失败并给出明确错误，不会带病运行。
- `/health` 的规则摘要随规则内容变化。
- 代码审查/检索确认生产代码中没有产品名硬编码。
- 删除或替换规则目录后，行为符合预期（启动失败或使用新规则）。

##### F-P0-12 交付文档与示例数据

**需求描述**：交付物必须能让未参与开发的人独立跑通并理解契约。

**业务规则**：

- README 包含：一键启动命令、接口说明、输入输出示例、规则文件说明、安全说明、常见问题。
- 提供示例输入，覆盖五类协议和至少一条 unknown。
- 文档中的字段、状态码、限制与实际行为一致。
- 不要求阅读源码才能运行。

**验收标准**：

- 新用户按 README 可在干净环境完成一次端到端识别。
- 示例输入可直接被 client 使用。
- 文档与 `docker compose config`、实际响应一致。

#### 2.1.5 P0 最小闭环判定

以下步骤全部通过，才视为 P0 完成：

1. 干净环境执行 `docker compose up --build`，构建成功。
2. server 在 5 秒内进入 healthy。
3. client 自动执行，输出包含 SSH、HTTP、MySQL、Redis、FTP 和 unknown。
4. `curl http://127.0.0.1:8080/health` 返回 200，规则数为正。
5. 发送畸形 JSON，返回 400，服务不退出。
6. 发送 10,000 条 unknown，返回 200，服务不 OOM、不超时。
7. `docker inspect` 验证非 root、只读根文件系统、capabilities 全丢。
8. 不重新构建镜像，新增一条规则并重启 server，新特征可识别。
9. 停止 server 后运行 client，client 以非 0 退出并给出清晰错误。
10. `docker compose down` 后无残留容器/网络。

任一步骤失败，P0 不通过。

### 2.2 P1 重要功能

- [ ] `docker compose ps` 中 server 为 healthy。
- [ ] `GET /health` 返回 200，`rules.count > 0`。
- [ ] client 输出包含五类协议和 unknown。
- [ ] 全部 unknown 返回 200，client 退出码 0。
- [ ] 畸形 JSON 返回 400，服务不退出。
- [ ] 10,000 条 unknown 返回 200，服务无 OOM。
- [ ] 非 root、只读根文件系统、capabilities 全丢。
- [ ] 不重编镜像新增规则并生效。
- [ ] server 停止时 client 非 0 退出且错误清晰。
- [ ] `docker compose down` 无残留。
